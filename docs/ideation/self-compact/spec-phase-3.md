# Implementation Spec: Self-Compaction, Phase 3

**Contract**: ./contract.md
**Phase**: Live acceptance and release integration
**Prerequisite**: Threshold controls and context UI
**Risk**: Medium
**Estimated effort**: M

## Technical Approach

Finish the package with behavioral acceptance, portable documentation, and release integration. Use the existing phase-1/2 tests, not another testing framework. Add a bounded real-model driver that launches actual Pi with only this extension, observes RPC/JSON events, and verifies a fresh handoff produces the exact requested file without a second human prompt. Do not report success based only on a scripted provider or an old `result.txt`.

The driver must fail on missing credentials, unsupported runtime/model, timeouts, skipped required scenarios, or incorrect evidence. Use the current configured provider/model when suitable, respecting existing authentication without printing or copying secrets. Defaults/token launches require >=300k context; the exact 1M marker fixture belongs in deterministic tests. Do not spend 250k tokens just to demonstrate flag parsing. Lifecycle checks use reduced, explicitly configured thresholds and enough real content for Pi to prepare a compaction.

## Decisions Considered and Rejected

- All requirements are MVP; no requested feature is deferred.
- Actual defaults are 225k soft, 250k warning, 20k buffer. Rejected percentage defaults; percentage values are explicit examples/tests.
- Reject incompatible window settings instead of silently scaling them.
- Note-driven completion and ordinary replay prevention, not a structured completion flag or arbitrary-crash exactly-once guarantee.
- Native successful /compact releases pending handoffs; no reimplementation of that command.
- Explicit retry preserves the saved note; no automatic retry scheduler.
- Package-relative editable prompts and widget, not global config writes or replacement footer.
- Build-compatible root re-export, matching local runtime verification, and package-local build without unrelated root upgrades.
- User approved narrow external writes to root README, this project's generated changeset, and necessary lockfile updates. Rejected stopping at planning under the original strict boundary.
- Critic revision requires a pre-build boundary comparison; do not claim unrelated work is preserved based only on tests.
- One print/JSON survival check is justified by headless autonomous operation; no cross-mode lifecycle matrix.

## Implementation Details

### 1. Real-model verification driver

**Patterns to follow**: `scripts/smoke-stack.sh` for standalone launches; Pi `docs/rpc.md` for protocol framing and events. Unlike optional CI smoke tests, this required acceptance driver must not exit 0 for missing credentials.

1. Verify runtime version >=0.86.1 and select an authenticated provider/model. Prefer current `PI_PROVIDER`/`PI_MODEL` when suitable; explicit driver arguments/environment may select another installed model without modifying global configs. Resolve auth through Pi, not by dumping environment or credentials.
2. Spawn Pi with other extensions/resources disabled and an explicit absolute `-e` path to the standalone extension. Avoid accidentally loading the user's extension suite twice. Scratch agent settings/session locations and artifacts must stay package-local or in tool-managed temporary runtime locations. Use a persistent session for reload scenarios, not `--no-session`.
3. Add a hard timeout and process-tree cleanup. Parse RPC lines by newline framing compatible with arbitrary JSON string content. Correlate command response IDs and actual events; don't treat a quiet timeout as success.
4. Before the live continuation scenario, remove only the driver-owned prior result/evidence. If result.txt predates the driver and ownership is unclear, refuse to overwrite user data. Use an isolated work session and exact absolute output path.
5. Send one initial task specifying the unfinished next action: write `packages/self-compact/result.txt` with bytes exactly `done` after self-compaction. Require a valid note-bearing self_compact call. The driver must not write result.txt itself or send another user prompt to make the continuation occur.
6. Observe tool call/result, compaction success, returned verbatim note, restored ordinary tools, autonomous continuation, real write tool call, and settled completion. Assert filesystem bytes exactly `done`, one successful handoff cycle, and no duplicate write. Record note/value/event identity and the assertion results in a sanitized JSON report.
7. Reload/resume the completed session and assert no handoff replay/provider request or rewrite. Include a completed-task note scenario: after delivery the model should report completion without repeating work. Verify actual write count and content/mtime rather than merely trusting prose.
8. Failure/cancel/reload/retry edge cases must already pass in deterministic real-Pi integration tests. Exercise at least one real failure/retry or cancellation/retry if the provider/session protocol supports controlling it reliably; do not replace deterministic race coverage with flaky sleep-based tests.
9. A prompt that intentionally fills context must be large enough for actual Pi compaction with its keepRecentTokens settings, yet small enough to avoid accidental repeated hard enforcement. Configure scratch test settings, not global user settings. Lower thresholds are for exercising behavior, not hard-coded production defaults.

**Feedback loop**: First test the driver's assertion and timeout logic with the existing deterministic provider, including a provider that never writes, writes `done\n`, rewrites the file, or never settles. These must fail. Then run `node packages/self-compact/verify/live.mjs` against real authentication. No fake-provider path may silently satisfy the live contract command.

### 2. Launch variants and command checks

Exercise standalone loading of all three forms:

```bash
pi -e "$PACKAGE/extensions/self-compact/self-compact.ts"
pi -e "$PACKAGE/extensions/self-compact/self-compact.ts" --compact-soft-at 100k --compact-at 200k --compact-buffer 50k
pi -e "$PACKAGE/extensions/self-compact/self-compact.ts" --compact-soft-at 20% --compact-at 50% --compact-buffer 0 --compact-prompt "Summarize the current goal, completed work, exact paths, test results, and next action. Do not invent completed work."
```

The driver may add RPC/print mode and isolation flags. Use /self-compact-info in RPC to assert actual resolved values and no model turn. Defaults/token cases need >=300k window. Use the deterministic 1,000,000-window fixture for exact 10%/20%/25% marker positions. Live checks must not fabricate the model's window or usage.

For literal summary override, capture actual request behavior with deterministic provider tests and verify real compaction succeeds with the literal instruction. A summary that happens to mention the requested topics is not proof of the system-message role; request-level tests provide that proof.

**Feedback loop**: `pnpm exec vitest run packages/self-compact/integration.test.ts -t 'human commands|prompt overrides|context widget'`, then the live command. Keep failures visible and nonzero.

### 3. Visible UI verification

Read the `verify-behavior` skill before driving the actual UI. Open a scratch Pi TUI with this extension and observe the 20-cell widget, thresholds, and info output. Confirm it coexists with the built-in/footer surface and command output does not create an LLM turn. Use supported checked UI tools with expected postconditions; save durable evidence inside the package. If screenshot tooling cannot capture this terminal, record a truthful textual terminal capture and the limitation rather than inventing `ui.png`.

Exact 40%-half-cached and token-marker values are deterministic RPC/widget assertions; the real UI check establishes that the registered widget is visible and usable, not a requirement to spend 400k real tokens.

**Feedback loop**: Launch the scratch TUI, inspect widget and info output, change model/config in a test session if safe, and compare with the unit/RPC expected strings. Report any unverified visual aspect explicitly.

## Failure Modes

| Component | Failure | Trigger | Impact | Mitigation |
| --- | --- | --- | --- | --- |
| Live driver | False pass from stale file | Result exists before run | No proof of continuation | Fresh owned fixture and event-linked actual write |
| Live driver | Auth or timeout treated as skip | Provider missing/unresponsive | False completion | Nonzero outcome and explicit blocker |
| Recovery proof | Extra prompt hides missing continuation | Driver sends follow-up | Broken autonomy passes | One initial task, no driver nudge before result |
| Packaging | Editable prompts absent | Dotfiles omitted from pack | Installed extension fails | Assert pack dry-run list and real load |
